# 05. 双向演进闭环（Meta-Evolution Loop）

> 理论支撑：P10（缺陷分布实证）、P14（从对话到贡献）、P16（性能—认知—责任采用）、P9（意图证据）
> 对抗失效：**元层失效**——"只修业务不沉淀规则"，导致同类缺陷无限复发
> 落地阶段：Phase 5（复盘与塔基升级）

## 1. 阶段目标

| 方向 | 名称 | 内容 |
|---|---|---|
| 正向 | **Forward Application** | 把本塔的规格引擎、契约、主动规则、安全关卡与形式化验证，应用到真实工程开发流中，压降 **AI 诱发缺陷率** |
| 反向 | **Reverse Evolution** | 把工程中**无法被现有规则覆盖的长尾缺陷与新型场景**提炼为模式，沉淀回本塔的策略、模板与规则库 |

一句话：**塔不是一次性交付的文档集，而是一个会因缺陷而变强的系统。**

## 2. 闭环总览

```
     ┌──────────────────────── 正向赋能 ─────────────────────────┐
     │  业务工程（任意项目）                                     │
     │  Phase 1 ─▶ 2 ─▶ 3 ─▶ 4 ─▶ 5                             │
     │   ▲ 规格/契约 ▲ 规则/举证 ▲ 关卡/边界 ▲ TDD/形式化        │
     └───────────────┬──────────────────────────────────────────┘
                     │ 暴露缺陷（测试失败 / 评审发现 / 线上问题）
                     ▼
     ┌──────── 机制一：Bug-to-Rule Feedback ─────────┐
     │ 归因：是哪个环节失控？（规格/契约/规则/边界/上下文）│
     │ 补丁：→ 反例防线（Negative Rule），即刻生效        │
     └───────────────┬───────────────────────────────┘
                     │ 周期性归纳（每 Sprint / 每轮迭代）
                     ▼
     ┌──────── 机制二：Meta-Iteration Protocol ──────┐
     │ 通用性判定 → 模式升级（core/ 或 extensions/）    │
     │ → 模板演进（templates/）→ 塔版本升级（vX.Y）    │
     └───────────────┬───────────────────────────────┘
                     │ 反哺
                     └────────▶ 下一轮项目的 AI 初始化天然免疫同类缺陷
```

## 3. 机制一：业务工程侧的 AI 故障收敛（Bug-to-Rule Feedback）

### 3.1 触发条件

在业务工程迭代中，当测试／质量活动／线上环境暴露**由 AI 生成代码引起**的逻辑漏洞、越权、死锁、
状态偏离或配置失控时触发（也包括"AI 做出未声明的隐含决策"导致的返工）。

### 3.2 因果归因（Root Cause Attribution）

**归因必须落到本塔的具体环节**，禁止停在"AI 写错了"：

| 归因结论 | 指向塔内环节 | 典型症状 |
|---|---|---|
| 规格边界没划清 | `core/01-spec-engine.md` | 一个节点承担多个职责；依赖未显式化导致漏改 |
| 契约有缺口 | `core/02-intent-contract.md` | 五槽位缺失（尤其"失败语义"）；断言未覆盖边界/失败路径 |
| 规则漏了约束 | `core/03-active-rules.md` | 该场景无规则条目；或规则不可判定导致未被执行 |
| 安全关卡未覆盖 | `extensions/01-security-gate.md` | 四类之外的新失效模式；或关卡被跳过 |
| 架构边界未声明 | `extensions/02-architecture-boundaries.md` | 改了"事实上的核心"却不在清单里 |
| 状态/不变量缺失 | `extensions/03-formal-reasoning.md` | 禁止迁移未列；不变量不可判定 |
| 验证流程失控 | `extensions/04-stabilization-workflow.md` | 无 RED；断言迁就实现；原型直通生产 |

### 3.3 补丁注入（Patch Injection）

| 步骤 | 动作 | 约束 |
|---|---|---|
| 1 | 把该次故障提炼为结构化**反例防线（Negative Rule）** | MUST 含真实反例（现象 + 触发路径 + 判定条件） |
| 2 | 注入当前工程的提示词或规则库，**立即生效**（不等塔版本升级） | MUST 在下一轮开工前生效 |
| 3 | 在迭代留存表中登记（`templates/iteration-checkpoint.md`） | MUST 留痕，避免反复踩同一坑 |

> 反例防线格式与 `core/03-active-rules.md` 的规则条目一致（七字段），`counterexample` 字段填本次真实缺陷。

### 3.3 补丁注入的四条硬性约束（★v0.5）

> 来源：真实缺陷回溯 —— ① 修复被做成「仅改显示」（页面看着有值，库里仍是空）；② 自动修复写库时**覆盖**了已有值；
> ③ 部分更新接口把「未提供」当成「显式置空」，把旧值清空（编辑表单未回填即提交）。

| # | 约束 | 判定 | 反例 |
|---|---|---|---|
| 1 | **修真实状态** | 修复 MUST 落在数据/逻辑层（落表或改判定） | 用展示层回落「补上」字段 ⇒ 库内仍空、问题被掩盖 |
| 2 | **幂等且只补空** | 自动/批量修复 MUST 幂等，且**只补缺失值**；MUST NOT 覆盖已有值（判据须落在查询条件里） | 无条件写该列 ⇒ 覆盖真实值 |
| 3 | **更新语义显式** | 部分更新接口 MUST 区分「未提供」与「显式置空」：未提供 ⇒ 不写该字段 | 表单未回填即写空 ⇒ 旧值丢失 |
| 4 | **留痕** | 自动修复 MUST 写审计/日志（谁触发、改了哪些行、改成什么） | 静默改数据 ⇒ 事后无法追溯 |
| 5 | **同族完备**（★v0.10） | 根因修复 MUST 覆盖**同族全部点位** —— 即"**同一个错误假设 / 同一处硬编码事实**"的**所有**使用点；逐点取证据，MUST NOT 只修被报告的那一处 | 只修报告点 ⇒ 其余点位继续按旧假设运行（"已修复"之后照样复发，且更隐蔽） |

## 4. 机制二：塔的元迭代协议（Meta-Iteration Protocol）

| 步骤 | 名称 | 动作 | 输出 |
|---|---|---|---|
| 1 | 归纳沉淀（Generalization） | 周期性（每 Sprint 结束）归类本周期收集的 AI 缺陷档案 | 缺陷归类表（按归因环节聚类） |
| 2 | 通用性判定 | 判断该模式是否**与具体业务无关**且**跨项目可能复现** | `通用 / 项目专属` 结论 |
| 3 | 模式升级（Pattern Upgrade） | 通用者修订 `core/` 或 `extensions/` 对应模块 | 模块修订提案 |
| 4 | 模板演进（Template Refinement） | 更新 `templates/` 使下一轮初始化天然免疫 | 模板修订 |
| 5 | 版本升级 | 按版本规则升级塔版本并留痕 | `README.md` 版本记录 |

### 4.1 通用性判据（准入塔基的硬门槛）

| 判据 | 说明 |
|---|---|
| C1 去业务化 | 剥离具体系统名、库表名、客户名后仍然成立 |
| C2 可复现性 | 在**另一个**不同技术栈/业务域的工程中也可能发生 |
| C3 可判定性 | 能写成"违反/未违反"的判定条件 |
| C4 有反例 | 至少 1 个真实反例支撑（无真实反例 ⇒ 降级为观察项） |
| C5 不重叠 | 不与既有规则重复（重复 ⇒ 合并而不是新增） |

**五条全满足 ⇒ 升入塔基；任一不满足 ⇒ 留在项目侧（就地生效）。**

### 4.2 塔版本号规则

| 变更类型 | 版本动作 | 示例 |
|---|---|---|
| 新增模块 / 改变执行阶段结构 | 主版本 +1 | `v0.1 → v1.0` |
| 新增或修订规则、模板、机制 | 次版本 +1 | `v0.1 → v0.2` |
| 措辞、示例、链接修正 | 修订号 +1 | `v0.2 → v0.2.1` |

### 4.3 工件生命周期与修订纪律（★v0.6）

> 来源：真实缺陷回溯 —— **工件之间自相矛盾**带来的返工与误导：历史记录被"顺手修正"、活工件未标注修订、
> 同一量在多处各有一份口径。典型症状：文档说已实现而实现未接线；两处计数不一致；旧结论仍被当事实引用。

| 要求 | 内容 | 硬性约束 |
|---|---|---|
| 工件分两类 | **活工件**（当前事实源：规格、规则库、清单）与**历史工件**（记录类：发布记录、归档结论）MUST 显式区分 | 混同 ⇒ 违反 |
| 历史冻结 | 历史工件 MUST NOT 回改；新结论一律以**新增条目**表达 | 回改历史 ⇒ 违反 |
| 活工件标注修订 | 结论变更 MUST 在活工件就地标注（何时 / 为何 / 依据哪个反例），旧表述 MUST 同步标注为已被修订 | 静默替换 ⇒ 违反 |
| 结论单真源 | 同一结论、同一统计量 MUST 只有一处真源；镜像点 MUST 由真源生成或由断言钉死（**加工单施加点**属同族要求 —— 对全分支成立的加工 MUST 在分派前统一施加，见 `core/02` §2.2b ★v0.12） | 多处各自维护 ⇒ 违反（改一处漏一处） |
| 口径冲突显式化 | 新旧口径冲突时 MUST 走显式取舍（豁免/回退/择一），MUST NOT 默认推翻旧口径 | 默认推翻 ⇒ 违反 |
| 生成规则单真源（★v0.8） | "生成规则"（命名 / 编号 / 路径 / URL）MUST 只有**一处真源**；**展示侧（预览）与落库侧、台账与实际生效面 MUST 引用同一真源**，MUST NOT 各自复写 | 多处各写一份 ⇒ 违反（预览与落库分叉、台账与实际不符） |
| **派生视图标注来源与时效**（★v0.10） | 派生 / 汇总 / 台账 / 缓存类展示（**非实时事实源**）MUST 显式标注其**来源与新鲜度**，并在存在**实时真源**时给出该真源的**可核对入口**（查询语句 / 链接 / 命令）；**有存储上限**的载体（截断日志 / 采样 / 摘要）MUST 标注**可能截断**，MUST NOT 被当作全文（见 `core/02` §2.4 ★v0.13） | 未标注 ⇒ 违反（使用者把派生数据当作事实；与之冲突的真源状态无人发现） |
| **真相优先级**（★v0.10） | 当派生视图与**实时真源**不一致时，对外结论 MUST 以**实时真源**为准；派生物 MUST NOT 被用作"是否生效"的判据（生效判定见 `core/02` §2.2d 读回核验） | 以派生物判生效 ⇒ 违反 |
| **判据可执行化**（★v0.11） | 每条判据 MUST 附带**可执行扫描动作**（"扫什么 / 命中即缺陷的样子 / 怎么扫"），并按 `templates/scan-playbook.md` 落成**项目侧清单实例**；判据集升版 ⇒ 清单 MUST 同步，且**覆盖度 MUST 由机械卡口校验** | 只写判据不写扫描动作 ⇒ 违反（判据退化为"归因字典"，缺陷只能"遇到才发现"） |
| **正向应用进闸门**（★v0.11 / **★v0.79 升格为阶段闸门**） | 正向应用（用判据**主动扫描**）MUST 落在**三处现场**：**设计评审预扫** → **缺陷定位先扫后改** → **交付校验**；交付校验 MUST 在**闸门内**完成。**★v0.79 起三处现场展开为六阶段闸门 G1–G6，且每个阶段 MUST 带产物**（设计前判据引用 / 设计后 design-check / 实现前扫描 / 实现后 apply-check / 校验 spec-check / 归档入塔）—— 落地骨架见 `templates/phase-gates.md` | **事后补档**（先改完再套判据）⇒ 违反（等于只有反向流，闭环少一半）；**闸门只在交付期存在**（设计 / 实现阶段无载体）⇒ 违反（靠人现场提醒 = 载体缺失） |
| **判据双层覆盖**（★v0.28） | 每条判据 MUST 同时覆盖**行为层**（真值表 / 用例 —— 证明"现在对"）与**结构层**（源码级检索 —— 该字面量 / 该写法**出现在哪**，拦"别处又写一套"） | 只有行为层 ⇒ 违反：能证明"判定写对了"，却拦不住同一判定在别处被再写一遍（这正是"改一处漏一处"类缺陷的成因） |
| **未裁定策略 MUST NOT 给结论性示例**（★v0.57） | 当某动作（删除 / 覆盖 / 迁移 / 清理）的**策略尚未裁定**时，交付文档 MUST 只登记"待裁定 + 待定项"，MUST NOT 给出**可照抄的执行示例**（命令 / 定时任务 / 语句） | 文档先于裁定给出示例 ⇒ 违反（读者按文档实施一个从未被裁定的策略 = **静默取得授权**） |
| **判据 / 用例清单 MUST「只索引、不重写」**（★v0.58） | 维护"全部判据 / 用例的清单"时 MUST 只**索引**既有实现（文件 + 用例名 + 维度标签），MUST NOT 为登记而复制一份实现；MUST **双向校验**（**僵尸条目**与**漏登记**都判红）且条目 **id 稳定**（新增只追加） | 复制实现 / 单向校验 ⇒ 违反（同一判据两处实现，清单与实现分叉） |
| **报告声明 ✅ MUST 逐点给证据**（★v0.58） | 校验报告里凡声明"✅ 已覆盖"的判据 MUST 给出**可复跑证据**（用例名或 `文件:行`） | 无证据的 ✅ 视为**未校验**（与"只写通过视为未校验"同源） |
| **入塔后 MUST 回扫存量**（★v0.59） | 新判据入塔（或入项目侧纪律）后，MUST 对**存量交付物**做一次**回扫**：把该判据当**探照灯**扫全仓，命中点**清单化**并逐条注明"合法例外"的理由；落地形态 = 清单**双向对齐**（新增命中变红 / 清单项消失也变红） | 只作用于"往后的变更" ⇒ 违反（教训已入塔，存量里的同族缺陷**原样躺着** ⇒ 换一条输入轴即复发） |
| **同族第二次复发 MUST 触发「族穷举」**（★v0.59） | 同一缺陷族**第二次**复发时，MUST 列出该决定的**全部时变输入**（配置 / 规则表 / 状态 / 外部事实 / 时点），逐条判定"**随单冻结** or **实时生效**"，并据此补卡口 | 只就新现场**再点修一次** ⇒ 违反（第一条轴修完即宣布"已修"，第二条轴从未被检查） |
| **声明与实现对账 MUST 双向且可机械核对**（★v0.60） | 交付面 MUST 维护**锚点表**（声明 → `文件:行` + 用例名）并**机械化核对**：**锚点漂移 / 声明找不到实现点 / 实现点没有卡口** 三类都判红；MUST NOT 只在文档里写"已实现" | 单向（只在文档声明）或人工核对 ⇒ 违反：声明与实现长期分叉，且**分叉不可见**（锚点漂移即"引用的证据已不是那条"） |
| **半实现 MUST 全轴记账**（★v0.60 / **★v0.82 补两轴**） | 判定某声明只实现了一半时，MUST 先列出该声明的**全部轴**（输入轴 / 分支轴 / 环境轴 / 时点轴 / **产出出口轴 / 消费入口轴** —— ★v0.82 补：同一声明对应**多个执行出口**或**多个写入入口**时 MUST **逐出口 / 逐入口**记账，见 `core/02` §2.2d ★v0.82）并逐条标注"**已做 / 登记未做**"（未做项 MUST 进交付说明的"未做"节）；MUST NOT 只补被现场暴露的那一轴（与本节「同族第二次复发 ⇒ 族穷举」同族） | 只修一轴、或把"登记未做"当已完成 ⇒ 违反：换一轴即复发，现象不同 ⇒ 难被认成同族 |
### 4.3a 流程闸门 MUST 版本无关（★v0.53）

> 来源：真实缺陷回溯 —— "每轮 MUST 做某件事"（如：用判据校验一轮并产出报告）的**唯一执行载体**是**某一版**的卡口里的一句断言；
> 之后的版本**没写这条** ⇒ 该环节整段被**静默跳过**，而交付物（代码 + 卡口 + 文档 + 产物）**看起来全绿**。
> 文档里写着、需求里写着，**没有任何机械力量**阻止跳过 —— 这不是"忘记"，而是**闸门断代**。

| 要求 | 内容 | 硬性约束 |
|---|---|---|
| 闸门载体版本无关 | "每轮 / 每版 MUST 做"的流程闸门 MUST 落在**版本无关**的卡口：从**版本真源**（版本记录 / 发布说明头部）解析"当前是谁"，再断言其交付物与必做项齐备 | 只写在某一版卡口里 ⇒ 违反（版本一前进即断代） |
| 断代反例 | 闸门 MUST 有**断代反例**：删掉"上一版"的那个卡口文件（或它那几句断言），闸门 MUST 仍然拦得住 | 删掉即失效 ⇒ 违反 |
| 两条流各有牙齿 | 正向（判据套用）与反向（缺陷 → 提案）MUST **各自**有机械断言；只钉一侧 ⇒ 另一侧可被静默跳过 | 只钉正向 ⇒ 违反（塔停止生长） |
| 报告结构断言 | 报告 MUST 由闸门断言其**必要结构**（锚定版本 / 逐项三值结论 / 缺陷归因 / 提案的未确认标注）；"只写通过"或"文件存在" ⇒ 视为未校验 | 只判"文件存在" ⇒ 违反 |
| NEVER | NEVER 把流程要求只写在文档或某一版卡口里；NEVER 用"文件存在"代替"内容合规" | — |

### 4.4 事前锚定：propose 阶段 MUST 产出版本锚定判据清单（★v0.53）

> 来源：真实缺陷回溯 —— 同一轮交付里，"事后校验"被静默跳过（见 4.3a）；再往前看，**事前**也未产出"本轮要守哪些判据、
> 锚定塔哪一版" ⇒ 判据套用变成**临时想起**（想起就做、忘了就没有），且事后报告**无法证明**用的是哪一版判据集（迭代轨迹断裂）。

| 要求 | 内容 | 硬性约束 |
|---|---|---|
| 事前产出 | propose / 设计阶段 MUST 产出**判据清单**：**锚定塔版本号** + 本轮适用判据条目（含 `extensions/01` 四类关卡）+ 每条判据的**可执行扫描动作**（可按 `templates/scan-playbook.md` 实例化） | 未产出 ⇒ 违反（设计阶段无判据基线） |
| 版本锚定与补注 | 清单 MUST 写明**塔版本**；交付校验时若塔已升版，MUST 在报告中**补注锚定变化**（如 v0.52 → v0.53），MUST NOT 静默复用旧判据集 | 不锚定 / 不补注 ⇒ 违反 |
| 逐项三值 + 证据 | 交付校验 MUST 对清单**逐项**给三值结论（已覆盖 / 缺陷 / 塔无条目）并附证据（`file:line` 或卡口用例名），MUST NOT 只写"通过" | 无证据 ⇒ 视为未校验 |
| 新空白有去向 | 出现"塔无条目"时 MUST 登记去向（塔版本提案），MUST NOT 就地放过 | 放过 ⇒ 违反 |
| NEVER | NEVER 跳过事前清单直接进入实现；NEVER 事后补写清单冒充事前产出（与 ★v0.11「事后补档」同族） | — |

### 4.4a 阶段产物闸门：闸门 MUST 按阶段留**产物**（★v0.79）

> 来源：真实缺陷回溯（已去业务化）—— 流程里"每轮 MUST 用判据校验一轮"的闸门**只存在于交付期**
> （见 §4.3a），于是**设计阶段**与**实现阶段**没有任何**载体**：没有产物、没有触发条件、没有卡口。
> 后果不是"忘记"，而是**执行者只能靠人现场提醒**（"你校验一轮吧"），而**提醒 = 载体缺失**（`core/03` §2.7）。
> 实测代价：某轮设计面 4 条缺陷里有 3 条本可在**设计冻结前**被拦下（判据当时已在手，只是没有"该产出什么"的约定）。

| 要求 | 内容 | 硬性约束 |
|---|---|---|
| **阶段闸门带产物** | 每个阶段（设计前 / 设计后 / 实现前 / 实现后 / 校验 / 归档）MUST 有**具名产物**（模板见 `templates/phase-gates.md`），且**触发条件是自动的**（"设计冻结那一刻"、"写第一行实现代码之前"），MUST NOT 依赖人喊 | 阶段无产物 ⇒ 违反（判定为该阶段**未过闸门**） |
| **产物三件套** | 三份阶段报告（设计后 / 实现后 / 校验）MUST 同口径：**锚定塔版本**（版本 + 提交号）+ **产出时机** + **逐项三值结论** | 缺任一 ⇒ 违反（无法区分"当时就过塔"与"事后补档"） |
| **产出时机诚实字段** | 产物 MUST 标注 `即时` 或 `补记（<原因>）`；**MUST NOT 伪装即时**；同一根因**重复出现** ⇒ 记为**载体缺陷**（补载体，不补报告） | 藏起"补记" ⇒ 违反（诚实性优先于好看） |
| **引用可达** | 每份产物 MUST 被**交付文档或变更文档引用** | 产物孤岛 ⇒ 违反（写完没人读 = 等于没做） |
| **MUST NOT 事后补档** | 漏做 ⇒ 该阶段判定为**未过闸门**；补一份文档**不改变**判定（与 §4.4 NEVER 同源） | 用补文档充数 ⇒ 违反 |
| **版本无关的机械载体** | 闸门的机械断言 MUST 落在**版本无关**的卡口（§4.3a）：从**版本真源**解析"当前是谁"，再断言各阶段产物**真实存在**且含上述契约 | 只判"文件存在"或写在某一版卡口里 ⇒ 违反 |
| **规模自适应** | 单行修复 / 纯文档格式改动 SHOULD 跳过并在交付说明写明理由（塔 `README` §4） | 硬套流程 ⇒ 违反（把判据变路障，见反模式 A14） |
| NEVER | NEVER 让"设计 / 实现阶段过塔"只存在于口头约定；NEVER 用"文件存在"代替"内容合规" | — |

### 4.4b episode 证据包：每轮交付 MUST 可审计（★v0.80 · P19 `arXiv:2605.13357`）

> 来源：harness（运行时基底）论文。核心论点：能力来自 **model–harness–environment 系统**而非模型单点；
> harness 的 **11 项组件职责**含**失败归因 / 验证 / 权限 / 熵审计 / 介入记录**；并以 **H0–H3 阶梯**与 **trace-based 评估**
> 把每次运行转成**可审计 episode 包**（低阶只产 patch；高阶产复现日志 / 归因 / 确定性需求检查 / 结构化验证报告）。
> 为什么并入本节（C5 合并优先）：本节已讲"缺陷处置四步 + 归因 + 卡口"，正好是该论文的**方法论侧**——缺的是"一次交付 = 一个 episode 包"的结构化表述与两项缺失职责。

| 要求 | 内容 | 硬性约束 |
|---|---|---|
| **交付 = 可审计 episode 包** | 每轮交付 MUST 能回答四问：**能否复现**（命令+输出）/ **归因给哪个环节** / **需求是否被确定性核对** / **结构化验证报告在哪** | 只留最终产物（patch / 改动清单）⇒ 违反（低阶 harness 形态：事后无法审计） |
| **两项缺失职责 MUST 记账** | ① **熵审计**：本轮是否让系统更乱（临时绕行 / 重复实现 / 口径分叉 / 死代码）；② **介入记录**：人介入的**时点 / 范围 / 依据**（与"两方案择优须人工确认"配套） | 不记账 ⇒ 违反（"更乱了"与"人改过什么"都无从追溯） |
| **H0–H3 自评 + 下一级台阶** | 项目 MAY 自评 harness 阶梯（H0 只产 patch → H3 产复现/归因/确定性检查/验证报告），MUST 登记**下一级台阶**（与常驻约束的级别口径同族） | 无阶梯 ⇒ 违反（只登记底线 = 判据路障化） |

### 4.4c 耗时入账与自行优化（Self-Timing Ledger，★v0.84 · 项目侧反演）

> 来源：项目侧反演（反例留项目侧）。形态：**验证成本恒定化** —— 无论改动多小，每轮执行同一套全量验证，
> 迭代节奏被验证时间线性拖垮；次生危害：人 / Agent 开始**回避跑卡口**（验证被静默跳过，比慢更危险）。
> 为什么入本节（C5 合并优先）：§4.4b 已把「一次交付 = 可审计 episode 包」——那是**结论维度**；
> 本节补**时间维度**：验证本身花了多少、花在哪，并让台账驱动自行优化。

| 要求 | 内容 | 硬性约束 |
|---|---|---|
| **验证耗时 MUST 入账** | 每轮验证 MUST 追加一行**机器可读台账**（tier / files / units / cached / fail / dur_s 等）；台账 schema 与分层语义（L0 受影响面 / L1 扩展面 / L2 全量门禁）MUST **语言无关** | 只有人类可读叙述、无机器台账 ⇒ 违反（无数据即无从自行优化） |
| **验证 MUST 分层且可见** | 日常迭代 MUST 只跑 L0/L1；L2 全量门禁仅发版/合并前执行；选择过程（验了什么、为何排除）MUST 打印 | 把 L2 当日常卡口每轮真跑 ⇒ 违反（本形态本体）；静默缩小验证范围 ⇒ 违反 |
| **台账 MUST 周期回看** | 按固定节奏汇总（每层均/最大耗时、缓存命中率、失败率），**优化候选由台账导出**（最慢用例 / 全量当 L0 用 / 不必要的禁缓存） | 凭印象宣称"变快了 / 更好了" ⇒ 违反（承接 `extensions/04` §2.4a 度量口径：口径缺一 ⇒ 结论未定） |
| **自行优化 MUST 走演进闭环** | 台账暴露的系统性耗时项 ⇒ 按本节 §4.1 通用性判据处置（过 C1–C5 才入塔）；**语言精确化**（反向依赖闭包 / 单用例画像 / 内置测试驱动）= **项目侧增强**，MUST NOT 回写塔 | 把单项目优化直接写进塔（含语言绑定实现）⇒ 违反 |
| **塔侧实现 MUST 语言无关** | 塔工件（引擎 / 契约 / 文档中的引擎描述）MUST NOT 内置任何语言的测试/构建命令路径——与「零业务」同级的强约束；语言绑定在**项目侧**做（引擎只认调用方注入的命令模板） | 塔内出现强绑定固定语言的实现 ⇒ 违反（由 selfcheck 机械检查引擎零语言命令字面量） |

**边界**：分层省的是**每轮重复验证**的时间，MUST NOT 砍 L2 门禁本身（否则 = 判据路障化，见 §8）；
缓存只允许在 L0/L1（工具链内容哈希缓存不掩盖新失败），L2 恒禁缓存真跑。

### 4.4d 阶段权限边界：锁清单与可写白名单（★v0.88 · 反向演进）

> 来源：项目侧反向演进（多阶段工作流复盘，经人工确认入塔）。重叠核对（C5）：
> `extensions/01` 关卡族管**运行时**权限（角色 → 接口）；「**工作流阶段 → 工件**」的过程可写面塔内确无对应 ⇒ 新增小节。

| 要求 | 内容 | 硬性约束 |
|---|---|---|
| **锁清单 + 可写白名单 MUST 显式声明** | 每个工作流阶段（探索 / 设计 / 实现 / 验证 / 归档等）开工时 MUST 声明：**锁清单**（本阶段只读的工件集合）与**可写白名单**（本阶段允许写入的工件集合） | 未声明即动工件 ⇒ 违反 |
| **自检四问** | 声明 MUST 能回答：本阶段锁了什么 / 能写什么 / 越界由谁拦 / 越界留痕在哪 | 四问缺答 ⇒ 违反 |
| **越界即停** | 实际写入命中锁清单或白名单之外 ⇒ **停止写入**并显式登记（越界项 + 原因 + 移交对象），MUST NOT 静默落盘 | 越界写入且未登记 ⇒ 违反 |
| **机器可判定** | 声明与实际变更集（diff）MUST 可机械对账：变更文件 ⊆ 可写白名单 | 对账不可行 ⇒ 违反 |

> 触发信号：多阶段协作中"顺手把别的阶段的产物也改了"——报告与工件分叉、回归无法归因。
> 与 §4.4a 的分工：§4.4a 管「每阶段 MUST 留**产物**」；本节管「每阶段只能动**哪些**工件」。

### 4.5 多选项裁决（择优）（★v0.61）

> 来源：真实缺陷回溯 —— **「择优」这一步被整体省略**：面对设计文档 / 复盘给出的多个候选，交付里只出现**选项清单**
> （"可做 A/B/C/D，请你选"），既无**判据列**也无**裁决列** ⇒ 决策不落地（**哪条都没做**），下一轮同一候选被重新提出；
> 更隐蔽的两种同族形态：**"一边倒"**（只列支持证据、不列代价与反对事实 —— 代价被系统性看不见）与
> **"沉默裁剪"**（悄悄不选，也不说为什么不选 —— 候选被误当作"已排除"）。

| 要求 | 内容 | 硬性约束 |
|---|---|---|
| **决策表 MUST 出现** | 候选 ≥2（或存在"采纳 / 改造后采纳 / 延后 / 否"的分支）时 MUST 出**决策表**：候选 → **判据列**（收益 / 代价 / 可回退 / 影响面 / 与既有口径是否一致）→ **裁决列** → **依据列**（真实反例或量测） | 只罗列候选、不给判据与裁决 ⇒ 违反（"**选项墙**"：把判断责任整体推回使用者） |
| **默认必须给裁决** | MUST 直接给出裁决；只有在**证据不足 / 代价不可估 / 需产品口径**时才允许"待裁定" | 用"你们选吧"代替裁决 ⇒ 违反（决策空转，通常**哪条都没做**） |
| **"待裁定" MUST 写清差哪个输入** | "待裁定" MUST 写明**缺哪一个输入**与"拿到后按什么判" | 泛化"待裁定" ⇒ 违反（等价于拖延：下一轮仍无人能判，且看起来"已登记过"） |
| **至少一侧是量测** | 收益与代价 MUST 至少一侧是**可核对量测**（命令输出 / 受影响文件数 / 复现步骤数 / 变更面清单 / 工时区间） | 全形容词 ⇒ 违反（无法比较，决策退化为偏好） |
| **反向意见 MUST 同列** | 决策表 MUST 至少列出一条**反对该裁决的事实或风险**（确无 ⇒ 明写"未发现"） | 只列支持面 ⇒ 违反（"**一边倒**"：代价与风险被系统性看不见） |
| **裁决 MUST 落地** | 裁决为"采纳"的 MUST **当场**落成代码或工件（与 `core/02` §2.2d「审计结论 MUST 落到代码」同源）；"否 / 延后"的 MUST 进交付说明的"未做 / 选项"节并写理由 | 裁决后不落地、或不写不选的理由 ⇒ 违反（"**沉默裁剪**"：候选被误当作"已排除"，或被重新提出） |
| **挂起态 MUST 收口，且收口 MUST 留痕**（★v0.62） | "延后 / 待裁定"是**挂起态**（非终态）：被裁决后 MUST **就地改裁决列**，并在**依据列保留"原判 + 差的输入"**；收口**只改记录**（"否"= 不做 ⇒ 不产生版本号前进）；卡口 MUST NOT 钉"裁决类目的分布"（只钉"每行有裁决 + 挂起为零 + 原判留痕在场"） | 直接删行 / 删理由 ⇒ 违反（**沉默裁剪**的合法外衣：看不出"曾经因缺输入而挂起"）；把挂起态留在表里 ⇒ 记录与事实分叉（下一轮被误读为"仍挂起"）；卡口钉分布 ⇒ 正确收口反被判红（断言钉了会合法变化之物） |
| **重扫来源 MUST 与既往终裁对账**（★v0.62） | 按外部建议清单（设计文档 / 评审意见 / 上游方案）**重新扫描**时 MUST 先与**既往终裁**对账：已终裁为"否"的候选再次出现 ⇒ **按终裁关闭并在决策表登记冲突**，MUST NOT 静默复活；新增候选 MUST 与终裁项**分列**（不得混在同一行判定） | 把已终裁项当"新发现"重提 ⇒ 违反（同一候选无限重提 = **沉默裁剪**的复发形态；决策空转、看起来"又在推进"） |
| **裁决 MUST 先报后行（人工确认门）**（★v0.65） | 存在**两种及以上可行方案**需要择优时，执行者 MUST **先把裁决与依据**（候选 / 判据 / 裁决 / 反向意见 / 影响面）报给决策人并**等待确认**，确认后才执行；**自动化 MUST NOT 用"直接执行"代替确认**（执行者不得自我授权）；确认留痕 MUST 可查（谁确认 / 何时 / 范围），且与既有「裁决 MUST 落地」配套（确认后 MUST 当场落地，MUST NOT 再挂起） | 未报即行 ⇒ 违反（把"执行"当"决策"：方案的成本与风险由决策人承担，却事后才知情；选错后的返工与信任成本远高于一次确认）；「报而不等」（同一轮既报又执行）⇒ 违反（等于没报）；用"默认方案"绕过确认 ⇒ 违反（**沉默授权**） |

**NEVER**：MUST NOT 只给"推荐"而不给"不选的理由"；MUST NOT 把**可判的事项**包进"待裁定"；MUST NOT 让决策表的**裁决列留空**；NEVER 让已终裁项在下一轮以"**重新扫描**"为名复活（★v0.62）；NEVER 用"删行 / 删理由"的方式收口挂起态（★v0.62）；NEVER 在存在两方案择优时未获确认就执行（MUST NOT 自我授权）。

### 4.5a 门类规则的首次落盘：自举豁免（★v0.88 · 反向演进）

> 来源：项目侧反向演进（经人工确认入塔；低频场景，按窄场景收口）。重叠核对（C5）：
> §4.5 管「多选项裁决」，本节管「**门自身还没存在时**怎么落第一块砖」⇒ 新增小节。

| 要求 | 内容 | 硬性约束 |
|---|---|---|
| **首次落盘走自举豁免并留痕** | 元规则 / 门类规则（约束"流程自身"的规则）**首次**落盘时，其门（卡口）尚不存在 —— 属自举：MUST 显式登记**自举豁免**（豁免对象 / 理由 / 本次用什么替代验证），MUST NOT 伪装成"门已生效" | 首次落盘自称已被门验证 ⇒ 违反（不诚实留痕） |
| **第二次起严格走门** | 同一门类规则自第二次变更起 MUST 严格走门（含回归既有同族卡口）；自举豁免 MUST NOT 成为常态豁免 | 第二次仍走豁免且无新理由 ⇒ 违反 |
| **机器可判定** | 自举豁免 MUST 留**可检索的留痕记录**；同族规则的非首次变更 MUST 能给出该门的执行证据 | 留痕缺失 ⇒ 违反 |

> 判定要点：**豁免的边界 = 门不存在的那一次**。豁免是"承认此时无法验证"，不是"免除验证义务" ——
> 留痕里 MUST 写清替代验证是什么（如同行评审 / 结构卡口 / 后补门）。

## 5. 执行工作流（Agent 必须交替执行）

| 步骤 | 名称 | 动作 | 输出物 | 硬性约束 |
|---|---|---|---|---|
| A | **Apply & Monitor** | 在工程开发中强制调用本塔各项防线（规格/契约/规则/关卡）；记录每轮迭代发现的 AI 缺陷与测试失败 | 缺陷与失败清单 | MUST 逐轮记录，不合并、不四舍五入 |
| B | **Post-mortem Diagnosis** | 对每个缺陷产出**结构化归因诊断报告**（现象 / 违背了哪条契约或规则 / 规避所需的最小改动） | `templates/bug-to-rule-postmortem.md` 实例 | MUST 归因落到塔内具体环节（见 3.2 表）；**首查顺序 MUST 是「先自证、后环境」**（★v0.30）：收到缺陷报告 MUST 先取证（读现象对应的代码路径 → 复现或**静态复现** → 取**客观证据**：日志 / 原始返回 / 卡口输出 / 产物指纹），**才**允许提出环境类假设；**任何归因（代码 / 环境 / 报告者）MUST 附「核对步骤 + 证据对照」**，MUST NOT 用**结论式**归因代替（"你没刷新吧"既无步骤也无证据） |
| C | **Tower Refactoring** | 依据诊断提出 `docs/`、`core/`、`extensions/` 的修订提案；**经开发者确认后**更新塔版本 | 修订提案 + 新版本 | MUST 人工确认；NEVER 未经确认就改塔 |

## 6. 硬性约束

**MUST**

- A 所有反哺塔的修改保持**通用抽象**（通过 4.1 的 C1–C5）。
- B 每个缺陷都有归因结论与去向（项目侧 / 塔基）。
- C 每次塔版本升级在 `README.md` 留痕（改了什么、为什么、依据哪个反例）。
- D 反例防线在**当轮**生效（不等塔版本升级）。
- E 塔内工件分「活工件 / 历史工件」：结论变更只在活工件标注修订，历史工件冻结（★v0.6）。
- F **派生视图标注来源与时效**（台账 / 缓存 / 汇总 MUST 标注来源与新鲜度，并给出实时真源的可核对入口）；真相冲突时以**实时真源**为准（★v0.10）。
- G 流程闸门 MUST 落在**版本无关**的卡口上，并有"删掉上一版卡口仍能拦住"的断代反例；正向与反向两条流 MUST **各自**有机械断言（★v0.53）。
- H propose / 设计阶段 MUST 产出**锚定塔版本**的判据清单（含可执行扫描动作）；交付校验逐项三值 + 证据，版本变化 MUST 补注（★v0.53）。
- G 每条判据 MUST **可执行化**（四元组：判据 → 扫什么 → 命中即缺陷 → 怎么扫），并按 `templates/scan-playbook.md` 落成项目侧清单实例；判据集升版 ⇒ 清单同步且覆盖度由**机械卡口**校验（★v0.11）。
- H 正向应用 MUST 落在**设计评审预扫 / 定位先扫后改 / 交付闸门内校验**三处现场（★v0.11）。
- I **缺陷归因 MUST 可复核**（★v0.30）：收到缺陷报告 MUST **先自证**（代码路径 / 复现或静态复现 / 客观证据），**才**提出环境类假设；任何归因（代码 / 环境 / 报告者）MUST 附「**核对步骤 + 证据对照**」，MUST NOT 用结论式归因代替；分歧 MUST 转成**可判定实验**（不因"报告者也可能有错"而不查，也不因"报告者说了"而不验）。

**NEVER**

- A **绝不允许**在业务出现缺陷时仅修复业务代码却不沉淀规则——必须走完
  "**缺陷出现 → 规则升级 → 塔演进**"的完整闭环。
- B **绝不**把特定业务的私有业务逻辑、硬编码变量或数据结构名写入塔的通用核心。
- C 绝不为了"显得完备"新增无真实反例的规则。
- D 绝不绕过人工确认自动改塔。
- E 绝不回改历史工件，或让同一结论/同一量在两处各持一份口径（★v0.6）。
- F 绝不把**派生视图**（台账 / 缓存 / 汇总）当作"是否生效"的判据，或让它以"事实来源"的姿态出现而不标注来源与时效（★v0.10）。
- G 绝不只写判据不写**扫描动作**（判据不可执行 = 只能事后归因）；绝不让清单与判据集不同步（★v0.11）。
- H 绝不**事后补档**正向校验（先改完再套判据 = 闭环少一半）（★v0.11）。
- I **绝不**在收到缺陷报告时以"环境 / 报告者"作为**首个**解释且**无取证动作**（★v0.30）；也**绝不**把"报告者说了"当作**免于验证**的理由（归因 MUST 可复核）。
- J **绝不**把流程要求只写在文档或**某一版**卡口里（版本一前进即断代、且无声）；**绝不**只钉单侧流（正向有牙齿、反向没有 = 塔停止生长）（★v0.53）。
- K **绝不**事后补写"事前判据清单"冒充事前产出；**绝不**用"报告文件存在"代替"报告内容合规"（★v0.53）。

## 8. 反模式

| 反模式 | 现象 | 后果 | 纠正 |
|---|---|---|---|
| 只修不沉淀 | Bug 修完就过 | 同类缺陷 Nth 次复发 | 立即走 B/C 步骤 |
| 归因甩锅 | "模型能力不行"；**报告者侧变体**（★v0.30）："你没刷新吧 / 是不是没重建 / 你操作错了 / 是不是缓存" | 无法改进任何环节（归因停在**外部**）；真缺陷被推迟发现；且把排查成本转嫁给**证据持有最少**的一方（报告者） | 按 3.2 表强制落到环节；**归因必须可复核**（★v0.30）：先自证（代码路径 / 复现或静态复现 / 客观证据），任何归因 MUST 附**核对步骤 + 证据对照**；**允许**环境假设与与报告者分歧，但 MUST NOT 用**结论式**归因代替；**报告者结论也可能有误** ⇒ MUST NOT 无条件采信，分歧 MUST 转成**可判定实验**（我看到的证据 + 请对方执行的一条命令及其期望输出） |
| 塔基污染 | 通用文档里出现业务表名 | 无法开源，复用性归零 | 剥离为通用表达 |
| 规则通胀 | 每个缺陷加一条规则 | 规则互相重叠、无人执行 | 先查重叠，合并优先 |
| 闭门改塔 | Agent 自行"优化"塔 | 塔偏离实际使用 | 人工确认后才改 |
| 只修报告点（★v0.10） | 被报告的那一处修了，同族的其余点位仍按旧假设运行 | "已修复"之后同类问题照样复发 | 走 §3.3 第 5 条：同族扫描 + 逐点取证 |
| 台账当事实（★v0.10） | 用派生的台账 / 缓存判断"是否生效"，且未标注来源与时效 | 与实时真源冲突时无人发现（假结论） | 标注来源与新鲜度 + 以实时真源为准 |
| 归因字典（★v0.11） | 判据只在**事后归因**时被引用，从不拿去做**主动扫描** | 缺陷靠"遇到才发现"（塔不产出发现能力） | 按 `templates/scan-playbook.md` 在三个现场执行清单 |
| 清单腐化（★v0.11） | 判据新增 / 改名后，项目侧清单不更新 | 清单与实际判据集脱节（守着旧清单空转） | 机械卡口校验覆盖度，不同步即阻断 |
| 事后补档（★v0.11） | 先改完再补正向校验 | 校验沦为形式（闭环少一半） | 校验进闸门内 |
| 闸门断代（★v0.53） | 流程要求只写在**某一版**卡口里；版本前进后那句断言留在历史 | 该环节整段静默跳过，交付物仍全绿 | 版本无关闸门 + 断代反例（删掉上一版卡口仍拦住） |
| 单向校验（★v0.53） | 只钉正向（判据套用有断言），反向（缺陷 → 提案）无断言 | 塔停止生长（只正反缺一即违规） | 两条流**各自**有机械断言（含报告结构断言） |
| 事后补清单（★v0.53） | 先实现完，再补一份"事前判据清单"充数 | 事前锚定失效，迭代轨迹断裂 | 事前产出 + 就地标注修订（不作事后补档） |
