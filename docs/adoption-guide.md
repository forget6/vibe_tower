# 部署与内嵌指南（Adoption Guide）

> 用途：把本塔**无缝内嵌**进任意项目 —— 从"放进目录"到"跑起来三段闭环"的完整落地路径、产出判据与提示词工程。
> 范围：**通用方法论**。本文件 `MUST NOT` 出现任何业务名、库表名、目录名、凭据、提交号或组织标识；
> 一切项目专属内容都写在**项目侧**的绑定与清单里（见 §3 第 4 步）。
> 真源：初始化提示词以 `templates/init-prompt.md` 为**唯一真源**；本指南解释其设计原则与适配方式，**不复制提示词正文**（避免两处副本漂移）。
> 理论支撑：`docs/research/research-base.md`（上下文先行 / 契约与断言 / 规则库演进三族）。

## 1. 目标：什么算"无缝内嵌"

| 硬性 | 含义 | 违反的后果 |
|---|---|---|
| **零构建零依赖** | 塔是纯文档 + 离线资料，放进去即可读可用，不改任何构建配置 | 引入安装/构建步骤 ⇒ 团队不敢放，或放了也不敢动 |
| **人的动作 ≤ 2** | ① 一条命令放置；② 一段提示词初始化 | 动作一多就变成"要排期的工作"，最后没人做 |
| **不侵入既有流程** | 复用项目已有的约定文件、测试目录、卡口命令；`NEVER` 另造一套体系 | 两套并行 ⇒ 权威冲突，旧的那套先死 |
| **可对账** | 任何时刻能回答"本项目的塔是哪个版本、按哪种方式生效" | 无从对账 ⇒ 塔的道德约束力归零（判据是否生效无人知） |

## 2. 部署架构（三层 + 两条贯穿线）

```
L0 塔层（只读方法论，零依赖，不生成项目文件）
        │  提供：判据 / 模板 / 阶梯 / 反模式
        ▼
L1 项目层：三类产出
   ├── 工件（人读）  ：功能地图 · 不可委托区 · 常驻约束清单 · 扫描清单实例 · 约定文件
   ├── 卡口（机器跑）：关键判据的可执行守卫 + 命令 + 实跑输出
   └── 对接配置（机器读）：版本与提交号 · 载体 · 入口 · 各路径 · 闸门 · 卡口命令 · 三段落点
        │  接线：设计评审预扫 / 缺陷定位先扫后改 / 交付闸门内校验
        ▼
L2 运行层：三段闭环
   事前规划（动手前）→ 事中守卫（施工中）→ 事后闭环演进（交付/缺陷后）
```

两条**贯穿线**（缺一条，上面的层就会退化成"文档堆"）：

| 贯穿线 | 作用 | 落地形态 |
|---|---|---|
| **A 版本对账** | 塔升版 ⇒ 项目侧知道"要不要同步、同步什么" | 对接配置登记**塔版本 + 提交号**，并与塔的版本真源**机械对账** |
| **B 成熟度阶梯 + 只减基线** | 横切要求（安全 / 审计 / 隔离 / 日志 / 权限…）不再靠提醒 | 每个横切维度登记**级别（L0 散落 / L1 声明 / L2 机器保证 / L3 自净）**与**下一级台阶**；存量违规登记**只减基线** |

> **为什么是这三层**：`L1` 让约束"存在"，`L2` 让约束"运转"，贯穿线让约束"长大"。
> 只有 `L1` ⇒ 一堆没人读的文件；只有 `L2` ⇒ 没有判据可跑的空转流程。

## 3. 五步内嵌（Step 0–4）

| 步 | 动作 | 判据（怎么算做到） |
|---|---|---|
| **0 放置** | 把塔放进项目：`git clone <塔仓> <项目>/<塔目录>`；备选：子模块（随塔升版）或与项目并列（两仓独立） | 塔目录在项目内可读；放置方式与团队协作习惯一致（提交进仓或忽略，二选一即可） |
| **1 选载体** | 让塔的规则落在"**施工期可见**"的位置：项目约定文件 / 编辑器规则 / 技能包 / 会话提示（可叠加） | 新成员按约定文件**就能上手**；`NEVER` 只放在某次会话里（会话结束即失效） |
| **2 初始化** | 把 `<塔目录>/templates/init-prompt.md` 的提示词交给 AI **一次**（替换占位符） | 产出三类七件（见 §5），且**卡口命令已实跑并附输出** |
| **3 接线** | 三处现场 + **三段闭环落点**写进对接配置 | 设计评审预扫 / 缺陷定位先扫后改 / 交付闸门各有落点；三段落点非空 |
| **4 对账** | 对接配置登记塔版本与提交号；塔升版时按 §8 同步 | 版本对账卡口可跑（配置里的版本 == 塔的版本真源） |

**规模自适应**：大仓/大团队**先覆盖 1–3 个模块**，其余显式写"未建立"；
`NEVER` 为了"一次做完"而把功能地图写成关键词堆（那会让地图变成负债）。

## 4. 提示词工程（这版提示词为什么有效）

初始化提示词的真源是 `templates/init-prompt.md`。它由**六条设计原则**支撑 —— 换项目时**只改占位符，不改结构**（结构本身就是判据的载体）：

| # | 原则 | 若违反会怎样 | 在提示词里的形态 |
|---|---|---|---|
| 1 | **先复述再动手** | "读完就写" ⇒ 语义漂移（写出来的不是要求的东西） | 第 0 步：读完先复述三件事（版本 / 不可委托区 / 要产哪几件） |
| 2 | **产出契约化** | 只读不产（聊完一圈，仓库里什么都没有） | 第 1–3 步逐件列名 + 归属类别（工件 / 卡口 / 配置） |
| 3 | **不做必须显式** | 静默跳过 ⇒ "以为做了" | 每题一句"本轮不做的 `MUST` 写「不做 + 原因」" |
| 4 | **判据内嵌** | 交付时才发现缺件 ⇒ 返工 | 每件产出旁挂**机器判据**（可核对，不是形容词） |
| 5 | **证据优先** | 卡口缺席（写了规则但没人执行） | 卡口必须"**实跑并附输出**"；命令写进对接配置 |
| 6 | **末步给下一步** | 部署完就停 ⇒ 塔退回"被读过一次" | 收尾输出"**下一步三件事**"，接上 L2 三段闭环 |

**占位符清单**（换项目时只填这些）：

| 占位符 | 含义 | 取值建议 |
|---|---|---|
| `<塔目录>` | 塔在项目内的相对路径 | 可见目录优先（更易被发现）；隐藏目录也可，但 `MUST` 在约定文件写明 |
| `<项目文档目录>` | 项目侧工件的落点 | 与项目既有文档惯例一致（`NEVER` 另造平行体系） |
| `<卡口落点>` | 机械守卫的位置 | 优先复用**既有测试/校验目录**，便于挂 CI |
| `<卡口命令>` | 交付闸门要跑什么 | 一行能跑完、失败即红（例：`<lint/测试命令>`） |
| `<本轮范围>` | 先覆盖哪些模块 | 1–3 个；其余写"未建立" |

**提示词的两条禁忌**：① `NEVER` 把项目业务细节写进提示词（提示词会被复用/外传）；
② `NEVER` 让 AI 自行"发明"判据 —— 判据来自塔的模板与项目既有卡口，`MUST` 有出处。

## 5. 产出清单与判据（三类七件）

| 类别 | 产出 | 通用判据 | 最小可用版 |
|---|---|---|---|
| **工件**（人读） | 功能地图 | 每个能力**都附可定位证据锚**；未知项显式；标注时点 | 覆盖 1–3 个模块，其余"未建立" |
| | 不可委托区 | 列出**必须人决策**的项且 ≥ 3 条 | 先列最关键 3 条 |
| | 常驻约束清单 | 每条含**机器判据 + 生效载体 + 只减基线 + 成熟度级别 + 下一级台阶** | 先做 1–2 个最痛的横切维度 |
| | 扫描清单实例 | 每行是**本项目动作**（判据 → 扫什么 → 命中即缺陷 → 怎么扫） | 先落 5–8 条最相关判据 |
| | 约定文件 | 写明"开工先读塔与清单、改完先扫" | 三行即可 |
| **卡口**（机器跑） | 机械守卫落点 | **命令可执行且已跑通**；至少覆盖：单一真源 / 静默失效 / 口径唯一 / 横切约束 / 存量基线只减 | 先落最痛 3–5 条判据的守卫 |
| **对接配置**（机器读） | 项目绑定 | 字段齐备；**版本与塔真源一致**；路径**真实存在** | 先填版本 / 提交号 / 各路径 / 卡口命令 |

> 判据的通用形态：**"可被第三方机械核对"**。凡是只能靠"我觉得差不多"的条目，都不算完成。

## 6. 三段闭环（落点写进对接配置）

| 环节 | 何时 | 做什么 | 证据 |
|---|---|---|---|
| **事前规划** | 动手**前** | 功能理解为先 → 规格节点 → 任务**每步带"验证："** → 复用参照（四分类差异清单）→ **契约与断言先行** | 每步有验证点；断言（含"必命中 / 必不误报"）；参照锚真实存在 |
| **事中守卫** | **施工中** | 常驻约束**施工期生效** · 预扫与**先扫后改** · 安全关卡 · **不可委托区人工闸门**（动作发生时拦） | 预扫/扫描记录（或显式豁免）· 卡口输出 · 关卡结论 · 闸门记录 |
| **事后闭环演进** | 交付 / 缺陷**后** | 跑卡口 → 缺陷归因（**Bug→Rule**）→ 去向（**合并入塔 / 项目侧自留**）→ 塔升版 + 项目侧同步 | 卡口实际输出 + 归因记录 + （若入塔）塔提交号 |

**判据**：三段**缺任一段落点** ⇒ 部署未完成；**有落点但跑不起来**（无命令 / 无输出）⇒ 同样未完成。

## 7. 反模式（出现任一即"内嵌失败"）

| 反模式 | 长相 | 纠正 |
|---|---|---|
| **只读不产** | 复述了塔的内容，仓库里没有任何落盘产出 | 三类七件 `MUST` 落盘；复述只是第 0 步 |
| **工件空壳** | 文件建了，但条目无证据锚 / 判据不可执行 | 按 §5 判据逐条自检 |
| **卡口缺席** | 只写清单，没有**能跑**的守卫（或跑了没输出） | 卡口 `MUST` 给出命令 + 实跑输出 |
| **塔条目照抄** | 扫描清单直接复制塔的骨架表 | 清单 `MUST` 是本项目动作（含具体命令/检索式） |
| **无对账** | 对接配置不写塔版本与提交号 | 登记版本 + 提交号，否则"跟随迭代"无从谈起 |
| **部署即停** | 初始化完成就结束，三段闭环没接上 | 部署的验收 = **三段跑起来** + 给出下一步 |
| **只拦不教** | 判据只有"禁止"，没有合规做法与下一级台阶 | 判据 `MUST` 带合规路径；横切维度登记级别与下一级台阶 |

## 8. 演进与对账（塔升版时同步什么）

| 塔侧变化 | 项目侧 `MUST` 同步 |
|---|---|
| 新增 / 修订判据、模板结构变化 | 扫描清单实例、常驻约束清单、映射表（塔条目 ↔ 项目卡口） |
| 版本号前进 | 对接配置的版本与提交号 |
| 新增模板 / 载体 | 若采用之，更新对接配置的路径；未采用则**显式写明不使用 + 原因** |
| 新增判据但项目侧**无落点** | 视为**同步未完成**（映射表不得出现"空映射"） |

**升级动作**：先读塔的版本记录**新增行**（改了什么 / 为什么 / 依据哪个反例），再核对受影响清单 —— `NEVER` 直接 `pull` 就继续用。

## 9. 常见环境适配（通用性）

| 环境 | 建议 |
|---|---|
| **单仓 / 多仓 / 子模块** | 三种放置都成立；判据相同（可读 + 可对账）。多仓时塔与项目**并列**并各自版本化 |
| **有 CI** | 把对接配置里的**卡口命令**挂进流水线 ⇒ 闸门自动生效（"交付闸门内校验"从纪律变成默认） |
| **无 CI** | 用最小纪律：交付前**跑一遍卡口命令**并把输出附在交付说明里 |
| **多团队 / 多语言** | 双载体（约定文件 + 编辑器规则）；判据用各语言等价形态表达（同一判据、不同工具） |
| **大仓 / 老项目** | 初始化**范围收敛**（1–3 个模块）＋ 存量违规登记**只减基线**，`NEVER` 一次性大改 |
| **高合规场景** | 常驻约束的"成熟度级别"与"只减基线"最有用：给审计一条**可核对**的收敛曲线 |

## 10. 部署完成自检（8 条）

1. 塔在项目内可读，放置方式与协作习惯一致；
2. 约定文件写明"开工先读塔与清单"（施工期可见）；
3. 三类七件齐备，或**显式写明不做 + 原因**；
4. **卡口命令可跑**（附实际输出），并写进对接配置；
5. 对接配置的**版本与塔真源一致**（对账可跑）；
6. 常驻约束每条含**判据 + 载体 + 级别 + 下一级台阶**；
7. 三段闭环**各有落点**（事前规划 / 事中守卫 / 事后闭环演进）；
8. 已给出**下一步三件事**（部署是起点，不是终点）。

> 8 条里任一条不满足 ⇒ 视为**未完成内嵌**；建议把这份清单落成项目侧的一个卡口（"自检"本身就是判据）。
