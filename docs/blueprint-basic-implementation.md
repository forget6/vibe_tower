# Vibe Knowledge Tower — 基本实现方案（Basic Implementation Blueprint）

> 第二步产物。输入：`docs/research/paper-analysis-whitebook.md`（机制级结论）。
> 输出：把机制转为**可落地的宏观工程实施逻辑**（分阶段路径），**不含任何编程语言代码**。

## 0. 定位与边界

| 项 | 内容 |
|---|---|
| 服务对象 | 任意使用 AI 编程助手的工程项目（**与具体业务完全解耦**） |
| 交付形态 | 结构化文档 + 检查清单 + 提示词模板（**不是运行时系统，不要求安装依赖**） |
| MUST | 只沉淀方法、机制、流程、清单；可独立打包开源 |
| NEVER | 写入任何业务项目的库表名、内部版本号、客户名、内部地址；不引入私有依赖 |

## 1. 总体骨架：三层防线 + 一条反馈回路

```
        ┌──────────────────────── 业务工程开发流 ────────────────────────┐
意图 ──▶ │ ① 规格与意图层  →  ② 约束与安全层  →  ③ 演进与验证层  →  交付 │
        └───────┬──────────────────┬──────────────────┬─────────────────┘
                │                  │                  │
         core/01 spec-engine   core/03 active-rules  extensions/02 boundaries
         core/02 contract      extensions/01 gate     extensions/03 formal
                                                      extensions/04 TDD
                └──────────┬───────────────────────────┘
                           ▼
                 extensions/05 meta-evolution-loop
              （缺陷 → 规则 → 塔基升级 → 反哺下一轮）
```

三层职责：
- **① 规格与意图层**：回答"要做什么、做到什么程度算对"（防 F1 上下文爆炸、F2 规格漂移、F3 隐性错误）。
- **② 约束与安全层**：回答"不允许做什么、如何证明没做"（防 F4 规则失效、F5 安全与配置失控）。
- **③ 演进与验证层**：回答"哪些不能动、如何证明真的对"（防 F6 架构侵蚀与随机性）。
- **反馈回路**：回答"错了之后塔怎么变强"（防"只修业务不沉淀规则"）。

## 2. 板块一：规格与意图层（Spec Engine & VibeContract）

### 2.1 意图 → 规格图谱（Intention to Spec Graph）

| 步骤 | 动作 | 输出物 | 硬性约束 |
|---|---|---|---|
| 1 | 把需求拆为**规格节点**（每个节点 = 一个可独立验证的语义单元） | `spec-node` 列表 | MUST 每节点有唯一 ID、责任边界、直接依赖 |
| 2 | 标注节点类型：`spine`（骨架／难点优先）／`feature`（边缘特性）／`constraint`（约束） | 节点类型标记 | MUST 先拉通 spine，再生长 feature（垂直切片） |
| 3 | 为每节点写**契约**：输入、输出、行为属性、失败语义 | 任务级契约 | MUST 契约可判定（能用断言表达）；NEVER 用"尽量""适当"等不可判词 |
| 4 | 建立节点间关系（依赖／包含／冲突） | 规格图谱 | MUST 冲突显式记录并当场消解，不得静默取舍 |
| 5 | 锁定本轮变更范围（本轮只允许触及哪些节点） | 范围声明 | NEVER 越范围改动 |

### 2.2 上下文收敛（Spine Context Assembler）

| 步骤 | 动作 | 输出物 | 硬性约束 |
|---|---|---|---|
| 1 | 依任务节点计算**直接依赖闭包** | 上下文清单 | MUST 只装载当前节点 + 直接依赖 |
| 2 | 屏蔽无关噪音（历史对话、无关模块、过期讨论） | 精简上下文 | NEVER 以"多给点总没错"为由全仓载入 |
| 3 | 标注每段上下文的**用途**（为何需要它） | 上下文注释 | MUST 每段上下文可回答"去掉它会错在哪" |

### 2.3 契约驱动的 QA（Contract-driven QA）

| 步骤 | 动作 | 输出物 | 硬性约束 |
|---|---|---|---|
| 1 | 契约 → 测试断言（先断言，后实现） | 断言集 | MUST 断言先于实现存在 |
| 2 | 开发者审核契约与断言（可视化确认） | 审核记录 | MUST 人工确认后才进入实现 |
| 3 | 实现后按契约回验，偏差即缺陷 | 回验结论 | MUST 偏差先记为缺陷再决定是否修订契约 |
| 4 | 把"用户可见行为"写成可见流约束（可检视、可静态化） | 可见行为约束 | MUST 对交互型产物定义"什么必须出现在哪" |

## 3. 板块二：约束与安全层（Zoro Active Rules & VibeGuard）

### 3.1 主动规则：前 / 中 / 后三段拦截

| 时机 | 拦截点 | 动作 | 输出物 | 硬性约束 |
|---|---|---|---|---|
| **前**（Plan） | 计划审核 | 把规则编号**锚定到计划的每一步**，无条件适用的规则单独列出 | 规则—步骤映射表 | MUST 每步至少标注 1 条规则；无适用规则的步骤须显式写"无" |
| **中**（Implement） | 执行期强制举证 | 每步提交时附"已遵守某规则"的证据（代码位置／测试／日志） | 证据条目 | MUST 证据可定位；NEVER 以"我认为已遵守"作为证据 |
| **后**（Verify） | 独立复核 | 逐条核对证据是否覆盖计划锚定的规则；缺口即回退 | 复核结论 | MUST 由独立于实现者的视角复核（角色分离） |

### 3.2 安全关卡（独立拦截墙）

| 步骤 | 动作 | 输出物 | 硬性约束 |
|---|---|---|---|
| 1 | 关卡覆盖面固定为四类：**越权访问／凭据与配置泄漏／发布与打包配置／外部输入信任边界** | 关卡清单 | MUST 四类每次全量执行（可加不可减） |
| 2 | 关卡与功能验收**分离**执行（功能全绿不等于关卡通过） | 双通道结论 | NEVER 以"功能已完成"跳过关卡 |
| 3 | 命中即阻断，修复后重跑关卡全量 | 阻断记录 | MUST 重跑全量而非只跑命中项 |
| 4 | 无法判定的项按"更严一侧"处置并登记 | 风险登记 | MUST 记录判定依据与责任人 |

### 3.3 规则库演进（现场反馈）

| 步骤 | 动作 | 硬性约束 |
|---|---|---|
| 1 | 现场发现规则不合用 ⇒ 当场提出规则修订提案（而非口头放过） | MUST 形成提案文本 |
| 2 | 提案经确认后更新规则库与模板 | MUST 更新后回写版本与变更理由 |
| 3 | 规则条目必须可判定、可举证 | NEVER 写入"写优雅代码"类不可判定条目 |

## 4. 板块三：演进与验证层（Context Before Code & Forge Pipeline）

### 4.1 不可委托区（Non-Delegation Zones）

| 步骤 | 动作 | 输出物 | 硬性约束 |
|---|---|---|---|
| 1 | 声明不可委托区清单（核心架构、对外契约、安全边界、数据模型红线） | `non-delegation.md` 式清单 | MUST 逐项写明"为什么不可委托"与"允许的例外流程" |
| 2 | 每次写码前完成架构上下文对齐（本次变更落在哪个架构位置、影响哪些契约） | 对齐声明 | NEVER 在未对齐状态下开始实现 |
| 3 | 变更准入：触及不可委托区 ⇒ 强制人工决策点（Agent 只能提案，不能实施） | 准入判定 | NEVER 由 Agent 自主修改不可委托区 |
| 4 | 边界漂移检查：定期比对"实际依赖"与"声明边界" | 漂移报告 | MUST 漂移项在下一轮开工前处置 |

### 4.2 轻量形式化（Invariants & State Machines）

| 步骤 | 动作 | 输出物 | 硬性约束 |
|---|---|---|---|
| 1 | 识别关键状态机（有状态流转、并发、权限、金额/额度类逻辑） | 状态机清单 | MUST 至少覆盖"状态集合 + 合法迁移 + 禁止迁移" |
| 2 | 为每个状态机写**不变量**（任何时刻都必须为真的断言） | 不变量清单 | MUST 不变量可判定 |
| 3 | 用轻量检查执行：非法迁移与不变量破坏必须被断言捕获 | 检查结果 | NEVER 以"路径很短"为由省略检查 |
| 4 | 需要更强保证时，走"意图 → 规约 → 演绎验证证据"的闭环 | 验证证据链 | MUST 证据先于结论；无证据不得声称已验证 |

### 4.3 TDD 协作流（Stabilization Workflow）

| 步骤 | 动作 | 输出物 | 硬性约束 |
|---|---|---|---|
| 1 | 先写断言并**确认失败**（RED） | 失败证据 | MUST 记录失败输出，不得跳过 |
| 2 | 最小实现使断言通过（GREEN） | 通过证据 | NEVER 为通过而放宽断言（断言变更须显式记录理由） |
| 3 | 重构并保持全绿（REFACTOR） | 全绿证据 | MUST 重构后全量复跑 |
| 4 | 留存**意图证据**：为何改、预期达成、依据哪条契约 | 迭代留存记录 | MUST 每轮迭代填写 `templates/iteration-checkpoint.md` |
| 5 | 高频试错点转化为参数或规则调整（收敛试错成本） | 试错收敛清单 | MUST 同一类返工出现两次以上即升级为规则 |

## 5. 三板块与执行阶段的对应

| Phase（见 `docs/agent-execution-phases.md`） | 主责板块 | 关键闸门 |
|---|---|---|
| Phase 1 意图对齐与规格锁定 | ① | 规格节点 + 契约 + 范围声明齐备 |
| Phase 2 主动规则注入与契约生成 | ①/② | 规则—步骤映射表 + 断言集 |
| Phase 3 边界检查与安全审计 | ②/③ | 不可委托区准入 + 安全关卡四类全量 |
| Phase 4 测试驱动与形式化验证闭环 | ③ | RED→GREEN→REFACTOR 证据 + 不变量检查 |
| Phase 5 迭代意图留存与复盘 | ③/回路 | 迭代留存 + 反例防线提案 |

## 6. 落地顺序（难点优先，垂直切片）

| 里程碑 | 内容 | 完成判据 |
|---|---|---|
| M1 骨架拉通 | 三层结构的文档与清单齐备，能在一次真实小任务上走完 Phase 1→5 | 走通一次且留下成套证据 |
| M2 规则固化 | 主动规则前/中/后三段落地，规则—证据绑定可复核 | 一次交付中每条规则都有证据 |
| M3 边界与形式化 | 不可委托区清单 + 关键状态机不变量 | 至少 1 个状态机的非法迁移被检查捕获 |
| M4 回路运转 | 反例防线与元迭代生效（缺陷→规则→塔基） | 至少 1 个真实缺陷转化为规则条目并回写模块 |

## 7. 有效性度量（判据，不含实现）

| 维度 | 指标 | 期望方向 |
|---|---|---|
| 返工 | 同一类缺陷重复出现次数 | 下降 |
| 上下文 | 单任务装载的无关文件数 | 下降 |
| 安全 | 安全关卡命中后"跳过关卡"次数 | 归零 |
| 边界 | 不可委托区被 Agent 自主修改次数 | 归零 |
| 沉淀 | 每 Sprint 由缺陷转化的规则条目数 | ≥1 且去向可追溯 |
| 可追溯 | 交付项能对应到规格节点与契约的比例 | 100% |

## 8. 非目标

- 不产出任何语言的实现代码或框架选型。
- 不替代项目既有的 CI/CD、代码评审、发布流程；本塔是**前置约束与验证层**。
- 不承诺自动修复缺陷；只承诺"缺陷可归因、可沉淀、可防复发"。
