## 2. 逐篇剖析（P1–P12）

### P1. VibeContract（`arXiv:2603.15691`，Song Wang，York University）
- **痛点**：LLM 生成代码"可编译、可运行"却含隐藏逻辑错误；氛围编程缺少 QA 的**对照基准**，"代码生成了，但不知对不对"。
- **核心机制**：契约优先（contract-first）——先把自然语言意图固化为显式契约，再以契约作为生成与校验的共同参照；把"对不对"从主观判断变为可核验的一致性判定。
- **映射**：`core/02-intent-contract.md` 的"任务级契约"；`docs/agent-execution-phases.md` Phase 1（锁定）与 Phase 5（对照复盘）；MUST：无契约不进入实现。

### P2. FlowCheck（`arXiv:2608.28880`，Columbia）
- **痛点**：氛围编程应用出现**静默行为失败**——界面看似正常，但用户可见信息没有流到预期状态或输出。
- **核心机制**：提供**约束语言**用于在应用界面层直接表达"用户可见信息流"约束；约束可被展示与人工检视（无需读码），且结构化程度足以支撑 LLM 可靠生成；约束最终被翻译为**确定性静态分析（CodeQL）**执行。
- **映射**：`core/02`（把意图写成"可见行为约束"而非模糊描述）；`extensions/03-formal-reasoning.md`（约束→确定性检查的翻译范式）；对应 Phase 3 的"可验证断言"。

### P3. Zoro（`arXiv:2604.15625`，Columbia）
- **痛点**：规则"写了但没被遵守"——静态提示词文件属**被动参考**，Agent 生成时并不真正受限。
- **核心机制**：三步主动控制网 —— ① **计划阶段规则锚定**：把规则贴到 Agent 计划的每一步；② **执行期强制举证**：要求 Agent 对每一步给出"已遵守某规则"的代码级证据（含单测）；③ 迭代闭环：现场纠偏并可沉淀回规则库。
- **映射**：`core/03-active-rules.md` 的"规则—证据—测试"三元绑定；Phase 2（规则注入）与 Phase 3（举证检查）；MUST：每步交付必须带规则证据。

### P4. The Spec Growth Engine（`arXiv:2606.27045`，Hartwig Grabowski）
- **痛点**：两类结构性失败 —— ① **上下文爆炸**（Agent 需一次性推理整仓，随上下文窗口填充而质量下降）；② **静默规格—代码漂移**（代码演进、规格不动，偏差在修复昂贵前不可见）。
- **核心机制**：① **机器可读规格图谱**：单体大文档拆为图节点，节点显式承载"契约/设计分离"；② **Spine 上下文收敛器**：限定 Agent 只装载当前任务路径及直接依赖；③ **漂移强制（drift-enforced）**：规格锚定且在代码变更时强制对齐。
- **映射**：`core/01-spec-engine.md` 全篇（图谱结构、收敛器规则、漂移检测）；Phase 1 的"路径级上下文装配"；是本塔对抗 F1/F2 的主干机制。

### P5. SWE-chat（`arXiv:2604.20779`，Stanford）
- **痛点**：Agent 在大规模采用，却缺少"真实用户如何使用、产出有多少真有用"的实证证据。
- **核心机制**：真实开源开发者会话的大规模数据集与持续采集流水线（约 6,000 sessions、63,000+ prompts、355,000+ tool calls），提供**行为分布**而非轶事。
- **映射**：`core/03`（规则强度应按真实交互分布设计，避免全部规则堆在同一处）；`extensions/04-stabilization-workflow.md`（以会话证据定位高频返工点）；Phase 5 复盘的量化输入。

### P6. VibeGuard（`arXiv:2604.01052`，Ying Xie，Kennesaw State University）
- **痛点**：真实事故——某 AI 编码 CLI 的 npm 包中误带 **59.8 MB source map**，暴露约 **512,000 行**私有 TypeScript；根因**不是逻辑错误而是打包配置错误**，而既有静态分析与密钥扫描工具**覆盖不到**该失效模式。
- **核心机制**：为 AI 生成代码设立**独立安全关卡**：把"生成特征相关"的失效模式（打包/发布配置、凭据与端口、越权）作为专门检查项，独立于通用 SAST。
- **映射**：`extensions/01-security-gate.md` 的关卡清单与放行条件；Phase 3 的独立审计入口；MUST：安全关卡不可被"功能已完成"为由跳过。

### P7. Context Before Code（`arXiv:2603.11073`，Tampere University）
- **痛点**：生产约束下缺乏氛围编程的经验报告；Agent 为快速实现功能而**破坏全局架构**。
- **核心机制**：**架构上下文先于代码**——动手前完成架构上下文对齐；显式锚定核心架构红线（不可委托区），使变更受制于顶层架构契约。
- **映射**：`extensions/02-architecture-boundaries.md`（不可委托区清单 + 变更准入）；Phase 1 的"边界声明"、Phase 3 的"越界检测"。

### P8. Vibe Coding Needs Vibe Reasoning（`arXiv:2511.00202`）
- **痛点**：常见代价是**技术债累积、安全问题、为达满意结果的反复改写**；作者归因于 LLM **无法调和逐步累积的人类约束**，而开发者又未能及时显式收敛这些约束。
- **核心机制**：引入**形式化验证思路**做推理层校验——把约束显式化并以轻量形式化手段监控内部状态与流转，减少隐性 Bug。
- **映射**：`extensions/03-formal-reasoning.md`（不变量与状态机契约）；Phase 3 的"约束累积台账"；与 P2 的约束语言互补（前者偏推理，后者偏可见行为流）。

### P9. Rolling the Dice（`arXiv:2512.22418`，UC Irvine／Southampton）
- **痛点**：氛围编程被宣传为生产率突破，但"实践者究竟如何定义与实践"缺乏证据；实践呈**高随机性试错**特征。
- **核心机制**：扎根理论定性研究——20 个氛围编程视频、7 场直播编码（约 16 小时、254 prompts）与 13 条观点材料，归纳实践模式与风险。
- **映射**：`extensions/04-stabilization-workflow.md` 的**意图证据留存**（记录"为什么改、预期达成、依据哪条契约"）；Phase 5 的复盘字段直接取自其风险项。

### P10. Understanding the (In)Security of Vibe-Coded Applications（`arXiv:2606.23130`）
- **痛点**：氛围编程把开发过程**实质委托**给 AI，安全性随之转移；需要实证的高危漏洞分布。
- **核心机制**：大规模安全审计与分类，凸显**越权访问（不充分授权）**与**配置失控**等高危类别，为防线排序提供依据。
- **映射**：`extensions/01` 的检查项优先级（越权与配置优先于风格类）；`core/03` 的"反例防线"（由真实缺陷反推规则）；Phase 3 必检清单。

### P11. Formal-Method-Guided Vibe Coding（`arXiv:2606.22413`）
- **痛点**：安全关键系统（DO-178C／IEC 61508／ISO 26262）下，仅"接受 LLM 生成源码、最少人工复核"**没有通向认证的路径**。
- **核心机制**：模型驱动工程 + 形式化方法闭环（Forge 式流水线）：把自然语言意图映射到可演绎验证的规约，自动生成验证证据，尽量免除人工编写形式化数学代码。
- **映射**：`extensions/03-formal-reasoning.md`（证据链形态）；`templates/iteration-checkpoint.md`（验证状态列）；Phase 4 的"证据先于结论"。

### P12. Vibe Coding: An Experiment with Test-Driven Development（`arXiv:2607.22406`，Moritz Mock, Barbara Russo）
- **痛点**：协作质量差会直接导致输出质量差；全自动模式引入了大量**未经验证的隐含决策点**。
- **核心机制**：设计并对比四种交互模型（人类单独／人—LLM 协作／全自动等），实证 TDD 协作流对质量与协作行为的影响。
- **映射**：`extensions/04` 的 TDD 协作流（实现前先生成结构化断言）；`templates/prompt-guidelines.md` 的标准执行流；Phase 4 的 RED→GREEN 纪律。

## 5. 结论：本塔的理论骨架

1. **主干闭环** = 规格图谱（P4）→ 任务契约（P1/P2）→ 主动规则与举证（P3）→ 独立安全关卡（P6/P10）→ 架构边界（P7）→ 轻量形式化（P8/P11）→ TDD 与意图证据（P12/P9）。
2. **校准源** = 真实交互分布（P5/P14）与采用代价（P16/P13）——规则强度不是拍脑袋，而是被证据校准。
3. **演进方式** = 反例防线 + 元迭代（P10/P14）→ `extensions/05-meta-evolution-loop.md`：Bug 出现必须换来规则升级。
4. **一句话**：氛围编程的风险不是"AI 不会写"，而是**约束在传递中丢失**；本塔的全部机制都在对抗这一件事。

> 本节的四条剖析**只做机制归纳**（不复制原文段落）；落点**优先并入既有节**（C5「先查重叠、合并优先」）。

### 5.1 P17 · 范式综述：**协作模式 MUST 显式声明**（`arXiv:2510.12399`）

| 项 | 内容 |
|---|---|
| **痛点** | 同一套判据在"无约束自动化"与"规划驱动"下**强度应当不同**，但实践中**没人声明本轮在用哪种模式** ⇒ 判据要么过严（逼执行者绕过）、要么过松（放行本应拦的改动）；综述另指出：成功**不只取决于模型能力**，而取决于**系统化上下文工程**与"人—智能体协作模式" |
| **核心机制** | ① 用**受约束 MDP** 刻画"开发者 × 项目 × 智能体"三角（约束即"不可违反项"）；② **五种模式**分类：无约束自动化 / 迭代对话协作 / **规划驱动** / **测试驱动** / **上下文增强**；③ 结论：**上下文工程是独立工程面**（不是提示词技巧） |
| **塔内落点** | **并入** `core/03-active-rules.md`：新增「**协作模式显式声明**」——每轮 MUST 声明本轮模式（∈ 五类），且**判据强度随模式分档**（无约束自动化 ⇒ 最强闸门；上下文增强/规划驱动 ⇒ 闸门可前置到规划）；`docs/agent-execution-phases.md` 增"阶段 ↔ 模式"映射；`core/01` 承接"上下文工程 = 规格与上下文收敛"（与既有 Spine 收敛器同族） |
| **为什么值得进塔** | 它把"判据强度"从**拍脑袋**变成**随模式声明** ⇒ 与既有「常驻约束」「阶段闸门」直接相乘，且**零业务信息** |

### 5.2 P18 · 参考架构：**意图 MUST 先解析为契约**（`arXiv:2510.17842`）

| 项 | 内容 |
|---|---|
| **痛点** | "把意图直接交给生成器"是**静默规格漂移**的结构性来源；且六类风险里 **reproducibility（可复现性）** 与 **explainability（可解释性）** 直接对应"事后无法解释为何这样生成" |
| **核心机制** | 参考架构四段：**意图解析器 → 语义嵌入引擎 → 智能体代码生成器 → 交互反馈环**；并与声明式/函数式/提示式编程对比（差异在**意图的表达层级**与**校验点位置**） |
| **塔内落点** | **并入** `core/02-intent-contract.md`：新增「**解析层 MUST 先于生成层**」——意图 MUST 先转成**结构化契约**（可校验、可复现）才允许进入实现；**可复现性**并入既有 §2.2b 指纹口径（同源重建同指纹）；反馈环并入 `extensions/03`（判据时点一致性） |
| **为什么值得进塔** | 给"契约优先"补上**解析层的位置定义**（此前只说"要有契约"，没说"契约从哪来、在哪一步产生"） |

### 5.3 P19 · harness：**能力来自 model–harness–environment**（`arXiv:2605.13357`）

| 项 | 内容 |
|---|---|
| **痛点** | 把不可靠归因于"模型能力"，于是**只换模型、不修基底**；一次改动"是否完成"**没有可核对的定义**（低阶 harness 只产出 patch） |
| **核心机制** | harness = **11 项组件职责**：任务规格 / 上下文选择 / 工具可达 / 项目记忆 / 任务状态 / **可观测** / **失败归因** / **验证** / **权限** / **熵审计** / **介入记录**；**H0–H3 阶梯**渐进暴露运行时支持；**trace-based 评估**把每次运行变成**可审计 episode 包**（高阶产出：复现日志 / 归因 / 确定性需求检查 / 结构化验证报告） |
| **塔内落点** | **并入** `extensions/05-meta-evolution-loop.md`（**episode 证据包**：每轮交付 MUST 能回答"能否复现 / 归因给谁 / 需求是否被确定性核对 / 验证报告在哪"）+ `extensions/01`（**权限**职责 ↔ 权限门）+ `core/03`（可观测 / 失败归因）+ `templates/verify-report-template.md`（对齐 episode 字段） |
| **为什么值得进塔** | 塔的"判据 + 卡口 + 留痕"正好是 harness 的**方法论侧实现** ⇒ 该论文给塔一个**外部同构参照**，也补上两个缺失职责：**熵审计**（改动是否让系统更乱）与**介入记录**（人介入的时点与范围） |

### 5.4 P20 · 度量纪律：**产出量 ≠ 生产力**（`arXiv:2608.20446`）

| 项 | 内容 |
|---|---|
| **痛点** | 同一现象出现 **+26%** 与 **−19%** 两种读数、代码评审时间 **+441%** ⇒ 若判据不声明"测量方法 / 范围 / 时间跨度"，**任何结论都能被引用**（判据退化为立场工具） |
