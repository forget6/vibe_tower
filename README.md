## 0. 塔能做什么（一句话：把"凭感觉交付"变成"可举证交付"）

氛围编程（vibe coding）的通病已被系统研究过：人机协作写代码会稳定复发**六类结构性失效** ——
上下文爆炸 · 静默规格漂移 · 隐性逻辑错误 · 规则失效 · 安全与配置失控 · 架构侵蚀与随机性
（逐条「痛点 → 核心机制 → 塔内落地位置」剖析见 [`docs/research/paper-analysis-whitebook.md`](docs/research/paper-analysis-whitebook.md)）。

依据不是"经验之谈"：塔的文献基座 = **20 篇 2025–2026 前沿论文（P1–P20）+ 机制映射白皮书**。
塔内模块以 `> 理论支撑：arXiv:<id>` 回指文献 ⇒ **每条判据有出处、可追溯**；论文清单与硬数据见
[`docs/research/research-base.md`](docs/research/research-base.md)（本节不展开）。

**你拿到的是**：**3** 个核心机制（`core/`）+ **7** 个扩展机制（`extensions/`，**62 小节**）+
**17** 条高频缺陷形态（`H1–H17`，每行自带检查动作）+ **22** 条反模式（`A1–A22`）+ **12** 份模板（`templates/`）
+ 入塔归因判据 **C1–C5** —— 全部落成**可复跑的卡口**，而不是"请务必注意"。

> **计数口径**：以上数字按**磁盘实测**校正（旧稿写作"42 小节 / 14 形态（H1–H14）/ 17 反模式（A1–A17）"，
> 已过期；★v0.84 本 README 的"48 小节"同为过期数字 ⇒ 校正为 52）。这类声称由闸门守着（`doc claims N extension
> sections == on disk` 等）—— **自 v0.84 起 README 自身的声称也在检查范围内**（此前闸门只读 SKILL.md，
> 本文件的过期数字漏网 ⇒ 补齐）。数字与磁盘不符即出厂失败。

### 0.1 三段闭环（**事前规划 → 事中守卫 → 事后闭环演进**；权威表述见 §4.7）

- **事前规划（动手之前）**：功能地图（能力 → `文件:行` 证据锚）· 规格节点切分 · 任务每步带"验证：" ·
  依赖复用对照 · 契约与断言先行（"必命中 / 必不误报"两侧）→ **产出**：任务计划 + 断言（可复跑）。
- **事中守卫（施工期）**：常驻约束在施工中生效（不靠提醒）· 变更预扫（扫描清单当探照灯）·
  缺陷定位先扫后改 · 四类安全关卡 · 不可委托区人工闸门在动作发生时拦 → **产出**：预扫记录（命中或显式豁免）+ 卡口输出 + 闸门记录。
- **事后闭环演进（交付 / 缺陷之后）**：交付闸门校验 · 缺陷处置四步（定性 → 取证 → 修因 → 固化）·
  归因判决（合并入塔 / 项目侧自留）· 塔升版 + 项目侧同步 → **产出**：卡口实际输出 + 归因记录 +（入塔则）塔提交号。

一句话记忆：**规划期把"要什么"写成断言；施工期让约束真的生效；交付后把教训变成规则。**

### 0.2 你能用它做什么（五个入口）

| 入口 | 你说 | 它做什么 |
|---|---|---|
| **接入** | 「把知识塔接进这个项目」 | 塔就位（**离线快照即可用**）+ 注入纪律 + 生成项目侧工件（功能地图 / 不可委托区 / 常驻约束 / 扫描清单 / 绑定） |
| **校验一轮** | 「用 vibe_tower 校验一轮」 | 锚定塔版本 → 逐条套判据 → **✅ 已覆盖 / ❌ 缺陷 / ⚠️ 塔无条目** 三值报告（可审计、可复跑） |
| **找 Bug / 修 Bug** | 「这个 bug 为什么反复出现」 | 形态编号定性 → 最小复现取证（两侧证据）→ 修机制 + 同形态全仓自查 → 留下可复跑卡口 |
| **跟塔升版** | 「拉最新塔并升版本」 | 自动 pull 塔、刷新包内快照、重建技能包、同步项目侧绑定（见 §4.6） |
| **本地自由生长 / 分支贡献** | —— | **默认本地自由生长**：项目侧规则与私有形态随便加、留项目侧、**不提交、不碰塔**；只有你愿意回馈时才自动建 `contrib/*` 分支提交（**提交前先确认**；守门：去私化 + 版本纪律） |

### 0.3 它不做什么（先划边界，省得误会）

不替你写业务代码 · 不做测试框架 · 不替代人工评审 · 不产出"看起来很美但抓不住"的结论 ——
**每条结论 MUST 附命令输出或 `文件#用例名`**。

**什么时候用**：用户说「用 vibe_tower 校验一轮」「找 bug 修 bug」「入塔」「沉淀规则」「缺陷归因」「为什么同一个 bug 反复出现」「拉最新塔」；
或你即将开始一个**多步改动**、需要在动手前把口径与卡口想清楚时。

**什么时候不用**（规模自适应，见 §4.5）：单行拼写修复、纯文档格式化、无共性的琐碎改动 —— 此时**跳过**，并在交付说明里写明"按规模自适应跳过"的理由，**MUST NOT 硬套流程**。
## 1. 设计哲学

氛围编程的风险不是"AI 不会写代码"，而是**约束在传递中丢失**：
需求丢一点、规则丢一点、边界丢一点，最后交付物看着对、实则偏离。
本塔的全部机制都围绕一件事：**让约束显式化、可执行、可举证、可沉淀**。

四条基本立场：

1. **Context Before Code**：先对齐规格与架构上下文，再写代码。
2. **Spec-Anchored & Contract-First**：没有契约与断言，就没有"对错"。
3. **Bug 必须换来规则**：缺陷不是修完就过，而是塔变强的输入。
4. **塔教项目演进，不只做卡口**：卡口只回答"这样不行"；塔 MUST 同时回答"**该往哪长、下一步长成什么样**"（落点见 §1.1）。

**为什么是「一把尺子 → 一座塔」**（★v0.69）：

> 单个项目的经验只值**一次**；把它**去业务化**成通用判据、再让**所有项目共享**，才值**无数次**。
> 所以塔同时追求两件事：它**懂你的项目**（项目侧工件 + 本地自由生长，越用越贴身），也**由大家喂大**（你贡献的每一条真实反例，都会变成所有人共用的尺子）。
>
> **为什么它能拦住常见 bug**：判据不是"请务必注意"，而是**可复跑的卡口**（命令 + 期望输出）；高频缺陷被固化成**形态目录**（每行自带检查动作，拿现象逐行对号即可定性）；修完的教训 MUST 换来**规则 + 卡口** —— 同一个坑不允许踩第二次。
>
> **为什么它能懂多维场景**：核心机制管**判据 / 意图契约 / 活动规则**，扩展机制管**安全关卡 / 架构边界 / 形式化推理 / 稳定化 / 元演进闭环 / 上下文学习 / 类比复用**，合起来覆盖**从判据到守卫再到演进**的多个维度（三段的权威表述见 §4.7，本节不复述该链）；而项目私有的维度（口径 / 约束 / 依赖）留在项目侧，**不污染通用面**。
>
> **它怎么长大（大量演进的机制）**：每一轮缺陷都走同一条路 —— **定性 → 取证 → 修因 → 固化**；新判据过 **C1–C5** 才入塔，且**先查重叠、合并优先**（绝不规则通胀）。于是塔的**版本号就是它的生长年轮**：`version.md` 里每一行都对应一次来自真实反例的演进，而不是"想当然的规则"。
>
> **一条诚实边界**：塔不替你写业务代码，也不承诺零 bug；它保证的是 —— **被检验过的教训不会只停留在"下次注意"**。
### 1.1 塔的双重身份：卡口是底线，**教演进**是本分（★v0.17）

> 背景：塔的机制天然会长成"**判据 + 卡口**"的形态 —— 它能**拦住**坏改动，却不会让项目**长大**。
> 只拦不教有三种典型失效：**路障化**（判据只写"禁止"，不写合规做法 ⇒ 执行者只能试错或绕过）、
> **判据通胀**（每轮只增判据、不增能力 ⇒ 规则越堆越厚，而项目本事没长）、**基线永存**（存量基线只登记不收敛 ⇒ "只减"变成"永远这么多"）。
> 因此"教"必须写成**可执行、可核对**的东西，而不是口号。

**（一）成熟度阶梯 L0–L3** —— "教"的内容 = 告诉项目**现在在哪一级、下一级台阶是什么**：

| 级别 | 特征（**客观可查**） | 升级动作（**可执行**） |
|---|---|---|
| **L0 散落** | 无声明、无判据；同一维度多处各自实现（逻辑 / 字面量散落） | 声明约束 + 把存量**量出来**（登记基线） |
| **L1 声明** | 有约定 / 清单，但**机器不查**（文档有、卡口无） | 把约定落成**机械判据**（扫描规则 / 卡口） |
| **L2 机器保证** | **单一真源** + 卡口 + 存量**只减**基线（新增违规必红，存量有数） | 逐轮**就近收敛**存量，直到基线清零 |
| **L3 自净** | 基线清零 / 无豁免清单；新增**天然合规**（约束的"豁免面"可被删除） | 保持（真源唯一 + 判据常驻）；该维度可让位给新维度 |

判定要点：每级 MUST 有**客观特征 + 机械检查方式**（"我们在哪一级"可由第三方核对，MUST NOT 靠自我感觉）；
升级动作 MUST 可执行（"建真源 / 加判据 / 登记基线 / 清零"），MUST NOT 是"加强意识""更加重视"这类**不可执行**表述。

**（二）"教"的四个动作** —— 分别回答"怎么做 / 在哪 / 去哪 / 为什么"：

| 动作 | 回答的问题 | 塔侧载体 |
|---|---|---|
| **教规范**（正向范式） | 怎么做才对 | 正向范式与复用参照（`extensions/06`、`extensions/07`）、常驻约束清单（`core/03` §2） |
| **定位阶梯** | 现在在哪一级 | 项目侧**常驻约束清单**逐条登记**成熟度级别** |
| **给下一级台阶** | 下一步该长成什么 | 同清单的「**下一级台阶（升级动作）**」＋ 存量**收敛目标** |
| **演进账本** | 为什么是这样 | 归因与留痕（`extensions/05`、本 README §7 版本记录）—— 使项目**继承**教训，而非重复踩坑 |

**（三）应用判据（可机械核对）**：项目侧常驻约束清单中，**每条约束 MUST 登记「成熟度级别」与「下一级台阶（升级动作）」**；
只写"禁止 / 要求"而不写"合规做法与升级动作" ⇒ 违例（判据**路障化**）。扫描动作见 `templates/scan-playbook.md`「横切维度成熟度与下一级台阶」。

**（四）反模式**：**A14 只拦不教**（判据无合规路径、无升级台阶 ⇒ 执行者只能试错或绕过）、
**A15 为拦而拦**（判据既不可判定、又无演进价值 ⇒ 规则通胀）。
与 A12 / A13 的区别：A12 / A13 治的是"约束没落地"，A14 / A15 治的是"塔只有底线、没有上方"。

## 2. 核心特性

- **完全解耦**：不绑定任何特定技术栈、业务域或组织；文档中不出现业务私名、库表名与凭据，可随时开源。
- **科学支撑**：建立在 20 篇前沿论文（12 篇主体 + 8 篇补位扩展）的机制归纳之上（见 `docs/research/`）。
- **AI-Native**：`docs/agent-execution-phases.md` 可直接作为 System Prompt / Agent 工作流使用。
- **可执行而非口号**：每个模块都含 输入 / 动作 / 输出物 / MUST-NEVER / 检查清单 / 反模式。
- **会自我进化**：`extensions/05` 定义了"缺陷 → 规则 → 塔基升级"的双向闭环。
- **Bug 有章法（★v0.34）**：缺陷处置四步「**定性 → 取证 → 修因 → 固化**」＋ 高频形态目录（H1–H12）＋ 归因判据 C1–C5（**§4.8**）——
  把"找 Bug / 修 Bug"从**手艺**变成**可执行、可举证、可机械核对**的动作。

### 4.7 部署之后：三段闭环（**事前规划 → 事中守卫 → 事后闭环演进**）

> 部署产出三类东西（§4.1）只是**接通电源**；项目日常按**三段**循环跑，**每段 MUST 有落点与卡口证据**（否则规则又回到"纸面"）。
> **口径留痕（★v0.25 修正）**：三段是 **事前规划 → 事中守卫 → 事后闭环演进** —— **规划在动手前**（想做对，先想清），
> **守卫在事中**（施工期就拦住，而非事后检查），**演进在事后**（把教训变成规则）。此前误作"事前守卫 → 规划"，方向已更正。

| 环节 | 何时 | 做什么 | 卡口证据（MUST 可核对） | 塔模块 |
|---|---|---|---|---|
| **事前规划** | 动手**前** | 功能理解为先（功能地图）→ 规格节点切分 → 任务**逐步带验证点**（"步骤 → 验证："）→ 复用参照（四分类差异清单）→ **契约与断言先行** | 任务计划每步都有验证点；断言文件（含"必命中 / 必不误报"）；参照锚**真实存在** | `core/01` / `extensions/04` / `extensions/07` / `core/02` |
| **事中守卫** | **施工中** | 常驻约束**在施工期生效**（不靠提醒）· 变更/评审预扫（把扫描清单当探照灯）· **缺陷定位先扫后改** · 四类安全关卡 · **不可委托区人工闸门在动作发生时拦** | 预扫/扫描记录（命中或显式豁免）· 卡口命令输出 · 关卡结论 · 闸门记录 | `extensions/01` / `extensions/02` / `core/03` §2 |
| **事后闭环演进** | 交付 / 缺陷**后** | 交付闸门内校验（跑 §4.3 的 **G 卡口**）→ 缺陷归因（Bug→Rule）→ 去向（**合并入塔 / 项目侧自留**）→ 塔升版 + 项目侧同步 | 卡口命令**实际输出** + 归因记录 + （若入塔）**塔提交号** | `extensions/05` |

> **落点登记**：三段的实际落点写在项目侧 `templates/project-binding.yml` 的 **`loop:`**（`pre_plan` / `during_guard` / `post_evolution`）—— 部署时一并填好。
> **判据**：三段**缺任一段的落点** ⇒ 部署未完成；有落点但**跑不起来**（无命令 / 无输出）⇒ 同样未完成（见 §4.3 退化清单「卡口缺席」）。
> **阶段自识别（★v0.31）**：任何"**校验 / 评审 / 检查**"动作 MUST **先声明所处阶段**，并**只取该阶段的判据集**；跨阶段判据 MUST NOT 互替（如"是否存在断言"属**事前 / 事中**，"卡口是否跑通"属**事中 / 事后**）。阶段所需输入**尚不存在**时（如事前阶段尚无断言文件、尚无产物），MUST 记为**该阶段的前置缺口**，MUST NOT 判为该阶段"失败"，也 MUST NOT 静默跳过。

### 4.8 找 Bug 与修 Bug（**缺陷处置四步**：定性 → 取证 → 修因 → 固化）

> **与 §4.7 的分工**：§4.7 回答「**什么时候**扫、每段谁负责」（三段闭环的时序与落点）；
> 本节回答「**单个缺陷怎么处置**」—— 四步**每步都带「可执行动作 / 可核对产出 / 可机械判据」**。
> 本节**只组装既有机制**（形态目录 / 扫描清单 / 归因判据 / Bug→Rule 模板 / 卡口纪律），**不新增规则族**；
> 全部动作**现在就能跑**，MUST NOT 写成"将来会支持"。

| 步 | 动作（可执行） | 产出（可核对） | 判据（可机械核对） |
|---|---|---|---|
| **① 定性** | 现象 → **形态目录**逐条对号（`docs/recurrence-catalog.md` 的 H1–H12，每行自带"检查动作"） | 命中**形态编号**；未命中 ⇒ **同轮登记**新形态（含"为什么高频"） | 归因记录 MUST 有**形态编号**或**显式未命中**；MUST NOT 只写"偶发 / 手滑 / 环境问题" |
| **② 取证** | **先扫后改**：把扫描清单当探照灯；取**最小可复现事实**（命令 / 输入 / 输出 / 时点） | 复现步骤 + 原始事实；"未命中"也要给**反证** | 事实 MUST **第三方可重跑**；结论 MUST NOT 建立在"应该 / 可能 / 我猜"上 |
| **③ 修因** | 修**产生缺陷的机制**（口径分裂 / 状态被压成一态 / 边界不明 / 静默失效），并**同形态全仓自查** | 修复 + 同形态落点清单（逐项：**已修** / **显式豁免 + 理由**） | 判据 MUST 落在**机制层**（单一真源 / 显式状态 / 显式边界）；只让当前现象消失 ⇒ **不算修复** |
| **④ 固化** | 归因判决（**合并入塔** / **项目侧自留**）→ 新判据 **MUST 带卡口**（可执行命令 + 实际输出）→ 入塔则升版 + 项目侧同步 | 归因报告（`templates/bug-to-rule-postmortem.md`）+ 卡口（`文件#用例名`）+ （若入塔）塔提交号 | 缺陷**未留下可复跑判据** ⇒ 视为**未闭环**（§1 立场 3：「**Bug 必须换来规则**」） |

**① 定性三问**（形态目录的正确用法 —— 三句都问完才算"定性"，只猜不算）：
① 现象最像 H1–H12 的**哪一行**（形态，而非"哪个页面"）？② 该行给的**检查动作**，本次**实际跑过**没有（跑了才叫定性）？
③ 全都不像 ⇒ 本轮**登记新形态**（附"为什么高频"），MUST NOT 让它只活在这次会话里。

**② 取证的双层口径**（与 `core/02` 一致）：新判据 MUST **同时**给「**必命中**」与「**必不误报**」两侧证据 ——
只给一侧，等于把误报面留给下一位执行者（他要么被误报拖住，要么干脆关掉判据）。

**③ 修因为什么必须"同形态全仓自查"**：形态是**机制层面**的（同一段"口径分裂 / 状态压缩 / 边界不明"通常有**多处落点**），
只修被报的那一处 ⇒ 同形态换个入口**必然复发**（这正是 A16 / A17 的失效路径）。

**④ 归因判决表**（两选一，MUST 显式写结论，MUST NOT 悬空）：

| 判决 | 何时 | 落地动作 |
|---|---|---|
| **合并入塔** | 过通用性判据 **C1–C5**（**脱敏后**仍有判据价值 / 可机械判定 / 不与既有条目重复） | **优先并入既有节**（合并优于新增）→ 塔升版（`version.md` 新增行：改了什么 / 为什么 / 依据哪个反例）→ 项目侧同步（映射 / 扫描清单 / 绑定版本与提交号） |
| **项目侧自留** | 含项目专属结构（私名 / 库表名 / 内部编号），或 C1–C5 任一不过 | 只进项目侧常驻约束清单与卡口；**MUST NOT** 塞进塔（否则污染通用性、破坏开源就绪） |

**本节的反模式**（编号沿用统一清单 `docs/agent-execution-phases.md`）：**A6 缺陷只修不沉淀**（同类复发）、
**A16 修完就过**（沉淀停在"口头/记忆"，未落成**可复跑卡口**）、**A17 按现象改文案**（只让现象消失，未修**机制** ⇒ 同族换入口复发）。

**每轮缺陷处置的收尾三件**：① 归因记录（含**形态编号**）；② **可复跑**的卡口（命令 + 实际输出）；③ 判决与去向（入塔 ⇒ 塔提交号；自留 ⇒ 项目侧清单与卡口路径）。

## 5. 与项目的解耦声明（开源就绪）
